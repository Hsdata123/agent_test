## Bug 1:ChatConversation UPDATE id 错位 (critical)

**文件:** `app/api/chat/route.ts:343`

```ts
// 修复前
await prisma.$executeRawUnsafe(
  `UPDATE ChatConversation SET title = ?, updatedAt = ? WHERE id = ?`,
  nextTitle, now, projectId   // ← 错: 应是 conversationId
);
await prisma.$executeRawUnsafe(
  `UPDATE ChatProject SET updatedAt = ? WHERE id = ?`,
  now, projectId
);
```

**影响:** 每轮对话都会执行,但 `ChatConversation` 的 WHERE 条件用的是 `projectId`,导致:
- 对话标题永远不更新 (下一行 ChatProject 用对了 id,所以 project 正常更新)
- 若 projectId 与 conversationId 不同,会触发外键不匹配错误

**修复:** 改为 `conversationId`。

## Bug 2:千川 token 刷新并发竞态 (critical)

**文件:** `lib/qianchuan/token-refresh.ts:20-31`

```ts
// 修复前
export async function getValidAccessToken(appId: string): Promise<string> {
  const existing = refreshLocks.get(appId);
  if (existing) return existing;

  const promise = doRefresh(appId);                  // ← 第一次 await 在 doRefresh 内部
  refreshLocks.set(appId, promise);                  // ← set 之前 doRefresh 已经 yield
  try {
    return await promise;
  } finally {
    refreshLocks.delete(appId);
  }
}
```

**竞态时序:**
1. Caller A 进入 `getValidAccessToken`
2. A 调 `doRefresh(appId)`,内部 `await getTokenByAppId(...)` yield
3. 此时 Caller B 也调 `getValidAccessToken`,看到 `existing === undefined` (A 还没 set)
4. B 也调 `doRefresh(appId)`,同样 yield
5. A/B 都跑 doRefresh 到底,各自调一次 `refresh_token` 接口
6. `refreshLocks.set` 被互相覆盖

**修复:**
```ts
const promise = (async () => {
  try {
    return await doRefresh(appId);
  } finally {
    refreshLocks.delete(appId);
  }
})();
refreshLocks.set(appId, promise);   // IIFE 返回后同步 set, 无 await 间隙
return promise;
```

## Bug 4:SSE controller 泄漏 (high)

**文件:** `app/api/chat/route.ts:240-273`

**修复前:**
- 成功路径 `send({type: "done", ...})` 后没调 `controller.close()`,ReadableStream 残留直到 Next.js 回收
- catch 里 `send` 和 `close` 任一抛异常都会让另一个不再执行,客户端可能收到半截流

**修复:**
- 成功路径: `send done` → 持久化 (失败仅记日志,不发 error 事件) → `controller.close()`
- catch: send 和 close 都包 try/catch,即使对方已关闭也不抛

## Bug 5:streamAnthropic 解析异常未捕获 (high)

**文件:** `lib/ithink.ts:622-709`

`streamAnthropic` 函数没有外层 try/catch,while 循环里 `decoder.decode(value, {stream:true})` 在 UTF-8 跨 chunk 切字符时会抛,会让 generator reject,`for await` 把异常冒泡到 SSE handler 中途断流。

对比:`chatStream` (chat completions / responses 两个分支) 有外层 try/catch 兜底,但 `streamAnthropic` 没有。

**修复:** 给 while 循环包 try/catch,异常时 yield 一个 error chunk + return,让 generator 正常结束而不是 reject。

> 注: `chatStream` 的两个 OpenAI 分支虽然外层 catch 会兜住,但 yield error 后 pending state (finalUsage / toolCallMap) 会丢失。这是已知遗留,本次未修。

## Bug 6:me/advertiser DELETE 事务不完整 (medium)

**文件:** `app/api/me/advertiser/route.ts:55-94`

```ts
// 修复前 — 多个 await 不在事务里
const binding = await prisma.userAdvertiserBinding.findUnique(...);
if (binding.isPrimary) throw ...;
await prisma.userAdvertiserBinding.delete(...);
if (user.advertiserId === advertiserId) {
  const remaining = await listUserAdvertisers(user.id);
  const next = remaining[0]?.advertiserId ?? null;
  await prisma.user.update(...);
  if (next) {
    await prisma.userAdvertiserBinding.update({...isPrimary:true});
  }
}
```

**竞态:** 两个并发 DELETE 都通过了 `isPrimary` 检查 (因为读和写中间有间隔),都执行了 delete,但晋升新主绑定时只有其中一个生效,另一个用户的 `advertiserId` 字段可能指向已被删除的 advertiser。

**修复:** 整段包到 `prisma.$transaction(async (tx) => {...})`,事务回滚保证原子性。

## Bug 7:rate-limiter 双重唤醒 (medium)

**文件:** `lib/qianchuan/rate-limiter.ts:21-49`

```ts
// 修复前
const onReady = () => {
  clearTimeout(timer);
  this.refill();
  if (this.tokens >= 1) {
    this.tokens -= 1;
    resolve();
  } else {
    reject(new Error("TokenBucket: unexpected empty bucket after wake"));
  }
};
this.waiters.push(onReady);
setTimeout(onReady, waitMs);    // ← 路径 1: per-waiter 定时器
```

`refill()` 内部:
```ts
while (this.waiters.length > 0 && this.tokens >= 1) {
  this.tokens -= 1;
  const next = this.waiters.shift();
  if (next) next();              // ← 路径 2: refill 触发
}
```

**bug:** 同一个 waiter 既在 `this.waiters` 里被 `refill()` 唤醒一次,又被自己注册的 `setTimeout(onReady)` 唤醒一次。第二次调用:
- 再次 `clearTimeout(timer)` (已 clear,无副作用)
- 再次 `this.refill()` 重新累加 token
- 再次 `this.tokens -= 1` 重复扣
- 再次 `resolve()` (promise 二次 resolve 静默 no-op)

**影响:** 单次 `acquire()` 实际消耗 2 个 token,严重时把限流上限跑穿。

**修复:**
- 去掉 per-waiter `setTimeout(onReady, waitMs)`
- 新增全局 50ms `setInterval` ticker 调用 `refill()`,保证没有新请求时队列里的 waiter 也能被唤醒
- 每个 waiter 只通过 `refill()` 触发一次,杜绝双扣

## Bug 9 (后续): 长 CJK 文件名导致 storagePath 损坏 (medium)

> KB E2E 测试发现 (`scripts/run_kb_e2e.sh` U-18,跑 200 字符的 CJK 文件名)

**症状:** 上传 200+ 字符的 CJK 文件名 (例如 `F-LONG-NAME-鱼子酱-抗老-紧致-种草-...txt`),接口返回 HTTP 500:

```
ENOENT: no such file or directory, open
'E:\\files-mentioned-by-the-user-web\\storage\\uploads\\1782799364979-...-F-LONG-NAME-ӽ'
```

**根因:** `lib/storage.ts:26` 的 `storedName = ${Date.now()}-${uuid}-${originalName}` 拼出来的全路径含 ~250 字符的 CJK 文件名,加上 Windows 上 Node 的 UTF-8 → UTF-16 → UTF-8 往返在 Prisma 写入时损坏部分 CJK (出现 `ӽ` 这种替代字符)。文件实际写到了正确路径,但 DB 中的 `storagePath` 字符串已损坏,后续 `fs.open(storagePath)` 找不到。

**修复:** 在 `safeFileName` 中加 `MAX_SAFE_NAME = 80` 长度截断,保留扩展名:

```ts
const MAX_SAFE_NAME = 80;
export function safeFileName(name: string) {
  const cleaned = name.replace(/[<>:"/\\|?*\u0000-\u001F]/g, "_").trim() || "file";
  if (cleaned.length <= MAX_SAFE_NAME) return cleaned;
  const dot = cleaned.lastIndexOf(".");
  if (dot <= 0) return cleaned.slice(0, MAX_SAFE_NAME);
  const ext = cleaned.slice(dot);
  if (ext.length >= MAX_SAFE_NAME) return cleaned.slice(0, MAX_SAFE_NAME);
  return cleaned.slice(0, MAX_SAFE_NAME - ext.length) + ext;
}
```

**验收:** U-18 PASS,KB E2E 全量 29/29 通过,`tsc --noEmit` 0 错。

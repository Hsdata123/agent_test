# 千川数据快照 (含 2025 历史导入 + 2026 同步)

## Context

千川实时 API 每次技能调用都返回 ~5K 字符，连续追问 token 消耗过快。优化方案：**把历史数据沉淀到 MySQL DB**，技能调用时优先查 DB，实时 API 只补最近 2 天（T-1 / T）。

**当前环境特殊**：
- 应用主库当前是 SQLite（`prisma/dev.db`，14 张表）
- **用户已有本地 MySQL**：`localhost:3306`，root/123456，库名 `oceanengine_api`
- **现有 MySQL 表**：`qianchuan_uni_promotion_video_data`，**170,687 行 / 2025-07-03 ~ 2025-12-31**，列名已与 API 字段对齐
- 用户明确：**现有 MySQL 是临时仓，以后会重做**（Phase 2 用 Docker Compose 起一套干净的）
- OceanEngine API 有频率限制，需要令牌桶限流 + 退避重试

**已确认决策**：
1. **存储粒度**：每日逐素材快照（沿用现有表列结构）
2. **2025 数据**：从现有表 **导入到新表 `QianchuanDailySnapshot`**（schema 统一，便于 Phase 2 迁移）
3. **2026 数据**：从 OceanEngine API 实时拉，**每日增量 + 首次全量回填**
4. **DB / 实时分界**：DB 覆盖到 T-2，实时 API 接最近 2 天
5. **输出格式**：保持现有 3 层摘要不变，新增 `meta.dbHit` / `meta.dbMissRange` / `meta.dataAsOf`
6. **API 限流**：令牌桶（默认 10 QPS）+ 指数退避重试（遇 429/5xx 退 1s → 2s → 4s，最多 3 次）
7. **租户**：单租户（多用户），不引入 `tenantId`
8. **Phase 2**：未来用 Docker Compose 重做，**当前 MySQL 数据导出 + 导入即可**

## 实施步骤

### 1. MySQL 连接与表结构

#### 1a. 新建 `QianchuanDailySnapshot` 表（**写入现有 MySQL 库**）

数据库连接：`mysql://root:123456@localhost:3306/oceanengine_api`

> 注意：**应用主库仍为 SQLite**（Prisma 现状），但 snapshot 表用 **直连 MySQL** 的方式读写。这是临时架构，Phase 2 切换统一 MySQL 后自然结束。

DDL（与现有 `qianchuan_uni_promotion_video_data` 列对齐 + 缺失字段补齐）：
```sql
CREATE TABLE IF NOT EXISTS QianchuanDailySnapshot (
  id              BIGINT AUTO_INCREMENT PRIMARY KEY,
  advertiserId    VARCHAR(32) NOT NULL,
  anchorId        VARCHAR(32) NOT NULL DEFAULT '',
  anchorName      VARCHAR(255) DEFAULT '',
  materialId      VARCHAR(64) NOT NULL,           -- 抖音号汇总时 = '_ACCOUNT_'
  materialName    VARCHAR(500) DEFAULT '',
  videoType       VARCHAR(64) DEFAULT '',
  statDate        VARCHAR(20) NOT NULL,            -- 'YYYY-MM-DD'
  smartBidType    VARCHAR(8) NOT NULL DEFAULT '0', -- '0' | '7'
  cost            DECIMAL(20,4) DEFAULT 0,         -- stat_cost
  gmv             DECIMAL(20,4) DEFAULT 0,         -- pay_order_gmv
  orderCount      DECIMAL(20,4) DEFAULT 0,         -- pay_order_cnt
  roi2            DECIMAL(10,4) DEFAULT 0,         -- prepay_pay_roi2
  couponAmount    DECIMAL(20,4) DEFAULT 0,         -- pay_order_coupon_amount
  subsidyAmount   DECIMAL(20,4) DEFAULT 0,         -- ecom_subsidy_amount
  showCount       DECIMAL(20,4) DEFAULT 0,         -- live_show_cnt
  clickCount      DECIMAL(20,4) DEFAULT 0,         -- live_watch_cnt
  ecpm            DECIMAL(20,4) DEFAULT 0,         -- total_ecpm
  cpc             DECIMAL(20,4) DEFAULT 0,         -- total_cpc
  source          VARCHAR(16) NOT NULL DEFAULT 'api',  -- 'api' | 'import' | 'backfill'
  syncedAt        DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  createdAt       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updatedAt       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uq_snapshot (advertiserId, anchorId, materialId, statDate, smartBidType),
  KEY idx_anchor_date (advertiserId, anchorId, statDate),
  KEY idx_advertiser_date (advertiserId, statDate)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

字段命名约定：与现有表一致用 **`snake_case`**（不是 camelCase）—— 这样 SQL 查询复用现有 2025 数据无摩擦。

### 3. `lib/qianchuan/rate-limiter.ts`（新）

### 4. `lib/qianchuan/snapshot-sync.ts`（新）

共用拉取逻辑：
- `syncRange({ advertiserId, anchorId?, smartBidType, startDate, endDate, source })`:
  1. `await rateLimiter.acquire()`
  2. 调 `callOceanEngine` + 分页（reuse `qianchuan-material.ts:116-142`）
  3. 逐行 upsert 到 `QianchuanDailySnapshot`（用 `INSERT ... ON DUPLICATE KEY UPDATE`）
  4. 遇 429 / 5xx 错误 → 指数退避（1s / 2s / 4s），最多 3 次后跳过本批次
  5. 打印进度 `[sync] +N / ~M / skip K / rate-limit R`
- `syncBackfill({ advertiserId, sinceDays } = { sinceDays: 30 })`: 全量回填（默认 30 天而非 90，因为 API 限制 + 现存 2025 数据已覆盖）
- `syncDailyIncrement({ advertiserId })`: 拉 `T-7 ~ T-2` 窗口

参数：
- `endDate = min(endDate, yesterday())` —— 永远不写"今天"
- `skipCache: true` —— 同步脚本不走 5min 内存缓存

### 5. `scripts/import-2025-history.ts`（新）

**导入现有 2025 数据到新表**，套用 `scripts/backfill-asset-aliases.ts:57-65` 入口模板：

```sql
INSERT INTO QianchuanDailySnapshot
  (advertiserId, anchorId, materialId, materialName, statDate, smartBidType, cost, gmv, orderCount, roi2, source)
SELECT
  advertiser_id, '', material_id, video_name, stat_time_day, '0',
  COALESCE(stat_cost,0), COALESCE(pay_order_gmv,0), COALESCE(pay_order_cnt,0),
  COALESCE(prepay_pay_roi2,0), 'import'
FROM qianchuan_uni_promotion_video_data
ON DUPLICATE KEY UPDATE
  cost=VALUES(cost), gmv=VALUES(gmv), orderCount=VALUES(orderCount), roi2=VALUES(roi2),
  materialName=VALUES(materialName), syncedAt=NOW();
```

注意：**`anchorId=''`（空字符串）**，因为现有表里没有抖音号字段；2026 数据填上真实 anchorId。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| OceanEngine API 限流（10 QPS 业内常见） | 令牌桶 + 指数退避（429/5xx 退 1s→2s→4s，最多 3 次）；超 3 次跳过本批次不阻塞后续 |
| MySQL 直连不在事务内，DB 临时仓期间可能挂 | `snapshot-store.ts` 用连接池 + try/catch；DB 挂时降级到全 API 模式（DB 失败抛错 → skill catch 后走原 API 路径） |
| 2025 数据 `anchorId=''` 导致后续按 anchorId 查询缺失 | 后续 `syncDailyIncrement` 会用真实 anchorId 写入新行；老空 anchorId 行用 `WHERE anchorId = ''` 隔离不影响新查询 |
| `materialId` 重复（同一素材跨多日） | `@@unique` 含 `(advertiserId, anchorId, materialId, statDate, smartBidType)` 5 列，自然 upsert |
| MySQL 8.0 默认认证插件不兼容 mysql2 | 客户端连接加 `insecureAuth: false`（默认走 caching_sha2_password 兼容） |
| Phase 2 切换时数据迁移 | 简单：`mysqldump oceanengine_api QianchuanDailySnapshot > snap.sql`，新库导入即可；表 schema 已在 Phase 1 用 MySQL DDL 写好，**无需重做** |
